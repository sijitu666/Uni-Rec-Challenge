推荐算法入门：OneTrans 与 HyFormer 图解

从一次刷淘宝说起，讲懂这两篇论文到底在做什么

① 推荐算法到底在解什么问题？

打开淘宝、抖音、B 站，你看到的每一张图、每一条视频，背后都有一个模型在悄悄回答一个问题：

核心问题："如果我把这个商品/视频塞给这个用户，他点的概率有多大？"

这个概率就叫 CTR (Click-Through Rate，点击率)。 系统会对几千个候选物品都算一遍 CTR，然后把概率最高的几个放在屏幕最显眼的位置。

一个简单的例子：小明刷淘宝

假设小明今天打开淘宝，系统手里有这些信息：

信息类型内容专业叫法
小明本人男，25 岁，杭州，最近常逛"运动鞋"用户特征
当前候选物品一双 Nike 跑鞋，899 元，4.8 分物品特征
当前情境晚上 22:00，WiFi 连接，首页 feed 流上下文特征
小明的历史过去 30 天点过的 50 个商品（带时间顺序）序列特征

前三类信息是"一个值就够了"——比如年龄就是 25。我们叫它 非序列特征 (non-sequential)。

最后一类不一样：它是一串有顺序的历史行为，最近的可能更重要，更早的可能不那么重要。 我们叫它 序列特征 (sequential)。

类比：这就像你判断一个朋友想吃什么：
  • "他是个广东人" → 非序列特征（一个标签就够）
  • "他这周连续吃了：火锅 → 烧烤 → 麻辣烫 → 川菜" → 序列特征（顺序很重要！下一顿大概率想吃清淡的）

② 为什么推荐系统也开始用 Transformer？

早期推荐模型（比如经典的 LR、Wide&Deep、DeepFM）擅长处理"特征交叉"——比如发现 "男性 + 运动鞋 + 周末"这三个特征组合在一起会让点击率显著上升。

但它们处理"用户的历史行为序列"很笨拙——通常就是把 50 个商品的 embedding 简单加起来求平均， 完全丢掉了顺序。

Transformer 在 NLP（ChatGPT 那一类）里证明了：它特别擅长处理"一串带顺序的东西"。 所以推荐系统的人就想：能不能把用户的"特征"和"历史行为"都当成 token， 一起塞进 Transformer 让它一次性搞定？

类比：把推荐场景想象成一个"翻译任务"：
  • 输入是：用户画像 + 历史行为 + 当前候选物品（一串"词"）
  • 输出是：一个分数（点 / 不点）
既然 Transformer 能把"中文"翻译成"英文"，自然也能把"用户状态"翻译成"点击概率"。

OneTrans 和 HyFormer 就是两种把推荐问题"塞进 Transformer"的不同思路。 下面我们一个一个看。

③ OneTrans：金字塔式的"信息浓缩"

论文：OneTrans - Unified Feature Interaction and Sequence Modeling with One Transformer

核心思想：把所有东西排成一串 token，然后慢慢"压缩"

OneTrans 把每条样本变成一长串 token：

用户 token
物品 token
情境 token
|
行为 1
行为 2
行为 3
…
行为 16

左边紫色的几个是 "非序列伪 token"（论文里叫 ns_tokens）， 它们其实是把用户/物品/情境这些"扁平特征"切成 ns_len 块（比如 3~4 块）， 每块投影成一个 token。

右边蓝色的是序列 token（用户的真实历史行为），按时间排好。

关键技巧 1：不同 token 用不同的"大脑"

标准 Transformer 里所有 token 共享同一套 Q/K/V 投影矩阵。 OneTrans 觉得这不公平——"用户画像 token"和"第 7 个历史商品 token"性质完全不同， 应该用不同的参数处理：

  • 前 ns_len 个非序列 token，每个 token 一套独立参数
  • 后面所有序列 token，共享同一套参数（因为它们性质相同，都是"历史行为"）
类比：想象你在面试一个人：
  • 问简历问题用一个套路（对应"用户 token"的专属参数）
  • 问技术问题用另一个套路（对应"物品 token"的专属参数）
  • 问"举几个项目例子"时，每个项目都用同一套追问模板（对应序列 token 共享参数）

关键技巧 2：金字塔压缩

每过一层，query 的长度就缩短一些，把序列信息一点点"挤"进前面的非序列 token 里：

第 1 层：8 个 query
第 2 层：6 个
第 3 层：4 个
最终：只剩 ns_tokens

最后只剩下前面那几个非序列 token，它们已经"吸收"了所有序列信息，被送进分类头算 CTR。

类比：就像你向老板汇报项目：
  • 第一遍：把 50 件事都讲一遍
  • 第二遍：合并成 30 件
  • 第三遍：合并成 10 件
  • 最后：浓缩成"3 句话总结"——这 3 句话就是要交给最终决策的"非序列 token"。

④ HyFormer：多支序列 + Query 解码

论文：HyFormer - Revisiting the Roles of Sequence Modeling and Feature Interaction in CTR Prediction

核心思想：用户的行为不是一条流，而是好几条平行的流

HyFormer 注意到一个现实问题：用户的"历史"其实有很多种类型，把它们硬塞进一条序列不太合理。 比如在淘宝里：

支线 1：点击序列

最近 16 个点过的商品

支线 2：购买序列

最近 16 个买过的商品

支线 3：搜索序列

最近 16 个搜过的关键词

HyFormer 把它们叫做 num_sequences 个序列分支，每条分支独立编码。 （在本仓库的代码里，因为 sample 数据里没有显式区分，所以是把检测到的序列特征自动均分到 3 组。）

关键技巧 1：为每条支线"造一个问题"（Query）

HyFormer 不让序列直接输出，而是先生成一些"问题 token"（query）， 再让 query 去"问"每条序列：

1
收集全局信息：把非序列特征 + 每条序列的"平均值摘要"拼起来， 得到一个能代表"用户当前状态"的全局向量。
2
生成 query：用这个全局向量过一个 MLP，为每条序列分支造几个专属的 query token。 你可以理解为："基于我现在的状态，我想去问点击历史的什么？想去问购买历史的什么？"
3
Query Decoding（查询解码）：每个 query 通过 cross-attention， 去对应的序列里"取答案"。
4
Query Boosting（查询增强）：把所有 query 的答案 + 非序列 token 丢进一个 MLP-Mixer 风格的小模块里互相混合，让"问到的答案"和"原始特征"再交互一遍。
5
反复几层后，把最终增强过的 token pool 一下，送进分类头。
类比：HyFormer 就像一个侦探破案：
  • 侦探（query）不是直接读完所有证人的笔录，
  • 而是先想好问题："死者最近见过谁？""有没有买过凶器？""有没有搜过相关地点？"
  • 然后有针对性地问每个证人（cross-attention）。
  • 最后把答案汇总到白板上重新组合（query boosting）。
比起 OneTrans"把所有信息排成一队从头读到尾"，HyFormer 更像"带着问题去查档案"，效率更高。

关键技巧 2：序列编码器有三种可选

模式做法类比
longer 用短 query 对长序列做 cross-attention 压缩 "用几个关键问题快速扫一遍 50 页文档"
full_transformer 标准的 Transformer self-attention "逐字逐句细读，每句都和其他句对照"
swiglu 纯 FFN，不用 attention "不互相对比，每条信息独立加工后再拼起来"，最快但最粗

⑤ 一图对比：OneTrans vs HyFormer

OneTrans

结构：单一 token 序列 + 金字塔压缩

序列形状：[B, 16, 45] 一条长流

核心动作：所有 token 排队 → 逐层"挤水"

参数策略：非序列 token 一个一个独立参数；序列 token 共享一套

类比："一锅炖" → 慢慢收汁

HyFormer

结构：多分支序列 + Query 解码 + Query Boosting

序列形状：[B, 3, 16, 15] 三条平行流

核心动作：先造问题 → 分头去问 → 答案再混合

参数策略：每条序列分支独立编码器，query 由全局信息生成

类比："分头侦察" → 汇总情报

它们要解决的"通用难题"是一样的

  1. 怎么把非序列特征和序列特征放进同一个模型？
  2. 怎么让模型不只是"加权平均"，而是真的理解顺序？
  3. 怎么压缩到最后只用很少的向量做出预测，又不丢信息？

OneTrans 的回答是"金字塔挤压"，HyFormer 的回答是"带问题查询"。这就是它们最大的分歧。

⑥ 训练流程到底在做什么？

这两个仓库都跑同一个数据集 TAAC2026/data_sample_1000（1000 条样本，800 训练 / 200 验证）：

1
数据加载：把每条样本变成 (非序列特征向量, 序列特征张量, 标签 0/1) 三元组。
2
前向：模型吐出一个 0~1 之间的概率（点击概率）。
3
损失：用二分类交叉熵 (BCE) 比对预测和真实标签。
4
评价：算 AUC（不是 accuracy！因为正负样本极不平衡，约 85% 都是"没点击"，全猜 0 也能拿 85% 准确率，但 AUC 才能反映模型真实区分能力）。
5
保存：每个 epoch 看 val AUC 是不是新高，是的话就 checkpoint。
当前结果： OneTrans 最佳 val AUC ≈ 0.51，HyFormer ≈ 0.53，都接近随机猜（0.5）。
这是正常的——只有 1000 条样本，主要用于代码跑通验证。真实比赛是百万级数据，差距会拉开。

⑦ 一页术语速查

术语白话解释
CTR点击率，模型要预测的目标
Token把任何东西（特征、行为）都变成一个等长向量，方便 Transformer 处理
Embedding把"商品 ID = 12345"这种离散值变成一个 64 维向量的查表过程
Attention"我（query）去看其他人（key），按相关程度加权平均他们的内容（value）"
Cross-attentionquery 来自 A，key/value 来自 B（"A 去问 B 问题"）
Self-attentionquery/key/value 都来自同一组 token（"自己跟自己对话"）
FFN / MLP普通的全连接前馈网络，作用是"再加工"每个 token
SwiGLU一种比 ReLU 更强的激活函数，被 LLaMA 等大模型广泛使用
AUC衡量模型对正负样本排序能力，0.5=随机，1.0=完美
AMP混合精度训练，用 fp16/bf16 加速，省显存

⑧ 想动手玩一下？

两个项目都可以一行命令跑通：

看模型骨架的 shape 流转（不需要数据）：

cd OneTrans_Pytorch && python main_pytorch.py

cd Hyformer_Pytorch && python main_pytorch.py

真正训练（会自动下载 1000 条样本数据）：

python scripts/run_taac2026_sample.py --epochs 5 --batch-size 32

建议读代码顺序：先 main_pytorch.py（架构本身）→ 再 models/taac_*.py（怎么包成分类器）→ 最后 scripts/run_taac2026_sample.py（训练流程）。
