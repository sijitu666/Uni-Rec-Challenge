OneTrans 与 HyFormer：论文 + 代码视角速读

目标：用“一页 HTML”把两篇方法的 motivation / method / experiments 讲清楚，并且从 模块输入输出、张量形状、数据流、训练脚本与数据格式 的角度对齐到你当前仓库的 PyTorch 复现。
注：本页面尽量避免引用无法从论文摘要/仓库文件直接核对的具体线上数值，重点以可复现的代码路径与 sample 实验为准。

先把问题说清楚：CTR 预测里“序列建模”和“特征交互”到底在干嘛？

这部分完全对齐本仓库的可运行实现：TAAC2026 sample 数据 → 张量化 → 训练脚本 → AUC。

任务与输出 (Task)

CTR/行为预测 = 分类

  • 训练目标：给定一条样本（用户、候选 item、上下文、历史行为序列），预测类别/是否点击。
  • 本仓库训练：使用 CrossEntropyLoss（二分类时等价于 softmax 版本的 log-loss）。
  • 评估：主指标是 AUC（样本类别不平衡时比 accuracy 更可靠）。

为什么要“统一骨干 / 统一交互”？

  • 传统范式常见路径：先压缩长序列 → 得到少量序列表征 → 再与非序列特征做高阶交互。
  • 两篇论文都在挑战这个“先压缩再交互”的隔离：它会让非序列信息无法早期影响序列建模，并且让模型扩展（更深/更宽）受限。

数据格式与张量化 (Data → Tensors)

训练脚本会从 HuggingFace 数据集 TAAC2026/data_sample_1000 读取样本，然后在 utils/taac_data.py 做 schema 检测与特征向量化。

非序列特征 non_seq

  • 标量特征：直接取值 → log1p 型压缩（避免极端数值）。
  • 数组特征：提取统计量（mean/std/min/max/last/length）拼到 non_seq 向量。
  • 本仓库 sample 实际维度：non_seq_dim = 183（见 run_metadata）。

序列特征 seq

  • OneTrans 版本：把所有序列通道堆成一个矩阵 [seq_len, seq_feature_dim]。
  • HyFormer 版本：为了对齐论文的“多序列分支”接口，把序列通道自动分组成 num_sequences 份，得到 [num_sequences, seq_len, seq_feature_dim]（不足维度会 0 padding）。
  • 本仓库 sample：OneTrans 的 seq_feature_dim = 45；HyFormer 分 3 组，每组 15 维（最大维度 15）。

训练流程 (Training Loop)

最小可复现实验

  • 数据切分：800/200（val_ratio=0.2，随机种子固定）。
  • 优化器：AdamW（lr=1e-3，weight_decay=1e-4）。
  • 自动混合精度：CUDA 上默认开启；CPU/macOS 默认关闭。

这份仓库当前跑出来的 best AUC

  • HyFormer（checkpoint: 2026-04-19 02:09:19）：best_val_auc = 0.5318
  • OneTrans（checkpoint: 2026-04-19 02:09:21）：best_val_auc = 0.5116
  • 解释：sample 数据仅用于代码验证，AUC 接近随机是正常现象；看方法差异主要看结构与可扩展性。

OneTrans：用一个 Transformer 同时做序列建模 + 特征交互

论文核心：统一 Token 序列 + 混合参数化 + 金字塔式查询长度缩减。仓库对应实现：OneTrans_Pytorch/main_pytorch.py + OneTrans_Pytorch/models/taac_onetrans.py。

Motivation：为什么要“统一”？

  • 打破信息隔离：传统两阶段（序列 encoder → 交互模块）让非序列特征无法早期影响序列表示。
  • 工程上更像 LLM：统一骨干更容易继承成熟优化（KV cache、flash attention、混精等）。
  • 可扩展性：把“序列建模能力”和“交互能力”放到同一个深网络里一起涨。

模块 I/O：从张量形状看 OneTrans（对齐仓库实现）

输入 → Tokenizer

  • 输入：non_seq_x 形状 [B, non_seq_dim]；seq_x 形状 [B, seq_len, seq_feature_dim]
  • 非序列 tokenizer：Linear → reshape 得到 [B, ns_len, d_model]
  • 序列 tokenizer：Linear 得到 [B, seq_len, d_model]
  • 拼接：[B, ns_len + seq_len, d_model]

输出 → Head

  • 金字塔压缩后只剩 [B, ns_len, d_model]
  • 池化：mean over tokens → [B, d_model]
  • 分类头：LayerNorm → MLP → logits [B, num_classes]
                    flowchart TD
                        A[non_seq_x\n[B, non_seq_dim]] --> B[Linear → reshape\nns_tokens [B, ns_len, d_model]]
                        C[seq_x\n[B, seq_len, seq_feature_dim]] --> D[Linear\nseq_tokens [B, seq_len, d_model]]
                        B --> E[concat\n[B, ns_len+seq_len, d_model]]
                        D --> E
                        E --> F[Base MultiOneTransBlock\n保持长度]
                        F --> G[Pyramid stack\n每层缩短 query_len]
                        G --> H[Compressed tokens\n[B, ns_len, d_model]]
                        H --> I[mean pool\n[B, d_model]]
                        I --> J[Head\nlogits [B, C]]

核心机制 1：Mixed Parameterization（“前缀 token 特化 + 其余共享”）

仓库实现里，注意力与 FFN 都采用“混合参数化”：

  • 前 ns_len 个 token（非序列伪 token）各自有独立的 Q/K/V 投影与独立 FFN。
  • 后面的序列 token 共用一组投影与一组 FFN。
  • 直观理解：非序列 token 语义差异大，需要“各管各的”；序列 token 结构更一致，适合共享以提升泛化并控参数量。

核心机制 2：Pyramid Compression（逐层减少 Query 长度）

  • 每个压缩 block 只让前缀的一部分 token 作为 Query，去 attend 全长度的 K/V。
  • 输出长度 = Query 长度，因此 token 序列会随深度逐层变短，直到只剩 ns_len。
  • 效果：把“序列信息”逐步吸收到前缀 token 里，后续任务只读这几个 token。

Mask 设计：origin / hard_mask / bimask_*

仓库实现提供 4 种注意力 mask（用于控制不同 token 之间能否互看）：

  • origin：来自原 demo 的“软 bias”式允许区域（非严格 -inf mask）。
  • hard_mask：把 origin 的允许区域做成严格 hard mask（禁止区域加 -inf）。
  • bimask_soft/bimask_hard：非序列 token 的 Query 全开放；序列 token 的 Query 按严格因果（只看过去）。

小提醒：在仓库实现里，origin 与 bimask_soft 更像是对注意力 logits 的“加性偏置”（soft bias），而不是完全禁止的 hard mask；hard_mask/bimask_hard 才会把禁止区域置为 -inf。

Experiments（论文报告，非本仓库 sample）

实验设置

  • 数据规模：约 29.1B impressions；用户约 27.9M；物品约 10.2M。
  • 任务：CTR 与 CVR（order）两类二分类；指标：AUC 与 UAUC（用户级加权 AUC）。
  • 对比基线（encode-then-interaction）：DCNv2+DIN 起步，逐步加强交互（Wukong/HiFormer/RankMixer）与序列（StackDIN/Transformer/LONGER）。
  • 效率指标：统计 dense 参数量（不含 sparse embedding）与训练 TFLOPs（batch size=2048）。

核心结论（摘取关键数值）

  • 统一骨干带来显著离线提升：论文表格报告 OneTransS 相对生产基线（DCNv2+DIN）在 CTR AUC/UAUC 约 +1.13%/+1.77%，CVR AUC/UAUC 约 +0.90%/+1.66%；OneTransL 进一步到 CTR +1.53%/+2.79%，CVR +1.14%/+3.23%。
  • 消融显示：Auto-Split tokenizer 优于手工分组；token-specific 参数优于完全共享；pyramid stack 能在几乎不损失效果的前提下降低计算（禁用 pyramid 会显著增加 TFLOPs）。
  • 系统侧：pyramid、跨请求 KV cache、FlashAttention、混精+重算各自对训练/推理的 runtime、显存、p99 latency 有明显贡献。
  • 线上：摘要中报告 OneTrans 带来 per-user GMV +5.68% 的 lift（具体线上指标以论文为准）。
  • 延迟对齐：论文示例里 OneTransL 的推理 p99 延迟约 13.2ms，与 DCNv2+DIN（约 13.6ms）同量级（说明“更大模型”可通过系统优化压到线上预算里）。

论文 vs 本仓库实现：你应该怎么对齐理解

  • 论文版输入更复杂：包含多行为序列、timestamp-aware 融合、[SEP] 分隔等；本仓库 OneTrans 版本用 TAAC sample 的单矩阵序列来跑通流程。
  • 论文强调的 KV caching / FlashAttention：这是系统与训练优化；本仓库重点在“结构复现 + 可训练脚本”，未实现生产级 serving 缓存。
  • 因此建议的阅读方式：先用本仓库把“张量怎么流/压缩怎么做/mask 怎么影响信息流”理解透，再回到论文看系统优化如何把统一骨干落地到真实延迟预算。

HyFormer：用“Query 解码 + Token 混合”把序列建模和交互揉进每一层

论文核心：反思长序列压缩的 query 设计，提出层内交替的 Query Decoding 与 Query Boosting。仓库对应实现：Hyformer_Pytorch/main_pytorch.py + Hyformer_Pytorch/models/taac_hyformer.py。

Motivation：HyFormer 在“统一架构”上更进一步的点

  • 批评点 1：只靠少量 query token 去压缩超长序列，query 信息量太贫，导致压缩出来的序列表征“视野狭窄”。
  • 批评点 2：交互通常发生在压缩之后（late fusion），让序列表示无法早期利用非序列上下文。
  • HyFormer 的答法：让“非序列信息 → query → 序列解码”与“跨 query/跨序列/跨特征混合”在每层交替发生，形成更深的双向信息流。

模块 I/O：从张量形状看 HyFormer（对齐仓库实现）

输入与分支

  • 输入：non_seq_x 形状 [B, non_seq_dim]
  • 输入：seq_x 形状 [B, num_sequences, seq_len, seq_feature_dim]
  • 分支 tokenizer：每个 sequence 分支各自 Linear → [B, seq_len, d_model]
  • 非序列 tokenizer：Linear → reshape → [B, num_non_seq_tokens, d_model]

输出

  • 每层输出的是“boosted token 序列”：[B, total_tokens, d_model]
  • 其中 total_tokens = num_sequences * global_tokens_per_seq + num_non_seq_tokens
  • 分类：mean pool → head → logits [B, num_classes]
                    flowchart TD
                        A[non_seq_x\n[B, non_seq_dim]] --> B[Linear → reshape\nnon_seq_tokens [B, NS, d]]
                        C[seq_x\n[B, S, L, F]] --> D[per-seq Linear\nseq_tokens[s] [B, L, d]]
                        D --> E[mean pool per seq\npooled_seq[s] [B, d]]
                        A --> F[global_info\nconcat(non_seq_x, pooled_seq*)]
                        E --> F
                        F --> G[per-seq MLPQueryGenerator\nquery_tokens[s] [B, Q, d]]
                        subgraph Layer[HyFormer Layer x N]
                            direction TB
                            G --> H[Query Decoding\nCross-Attn: query→sequence]
                            D --> H
                            B --> I[Query Boosting\nMixer over (decoded_queries + non_seq_tokens)]
                            H --> I
                            I --> G
                        end
                        I --> O[Output tokens\n[B, total_tokens, d]]

核心机制 1：Query Generation（global_info → per-seq queries）

仓库实现选择了一个很“工程友好”的生成方式：

  • 先对每个序列分支做 masked mean pool，得到每个分支的全局摘要向量。
  • 把 non_seq_x 与所有分支摘要拼成 global_info。
  • 每个序列分支都有独立的 MLP 生成器输出自己的 query token（数量为 global_tokens_per_seq）。

核心机制 2：Query Decoding（queries cross-attend to sequences）

  • 每个序列分支先过一个 sequence encoder（可选 longer / full_transformer / swiglu）。
  • Query decoder 是 Cross-Attention：query_tokens[s] attend 到该分支编码后的序列 tokens。
  • 输出是 decoded queries：仍然是 [B, Q, d_model]，但语义已经“读过序列”。

核心机制 3：Query Boosting（Mixer 让跨序列/跨特征交互发生在每层）

  • 把所有分支的 decoded queries 与 non-seq tokens 拼起来：[B, total_tokens, d]。
  • QueryBoostMixer 做 token mixing：把通道维度重排成“每个 token 拿到一个子空间”，再在 token 维度上做 MLP 混合，最后残差回去。
  • 直观：这一步提供了高效的 cross-query / cross-sequence / query-to-feature 混合通道。

sequence encoder 的三种模式（仓库实现）

  • longer：先把长序列做 chunk pool 到 short_seq_len，再用 cross-attn 读全长序列。
  • full_transformer：标准 self-attention 编码序列。
  • swiglu：不做注意力，只做 SwiGLU FFN（更轻量，适合做对照/消融）。

Experiments（论文报告，非本仓库 sample）

实验设置

  • 场景：字节跳动 Douyin Search CTR 预测；数据：约 3B samples（70 天日志子集）。
  • 多序列：long-term（最长 3000）、search top-50、feed top-50 三类主序列。
  • 两类基线：传统两阶段（LONGER/Full Transformer + RankMixer/Transformer/Wukong）与统一架构（MTGR/OneTrans）。
  • 指标：Query-level AUC；并报告 dense Params 与训练 FLOPs（batch size=2048）。
  • 实现细节：MLP-Mixer 的 token 数对齐到 16；论文中的 HyFormer 配置示例是 13 个非序列 token + 3 个 global token（每个序列 1 个）。

核心结果（摘取关键数值）

  • 总体：HyFormer 在该工业数据上取得最高 AUC（文中表格给出 0.6489），并且在 FLOPs 上更省（示例配置约 3.9×10^12）。
  • 对比（论文表格示例）：LONGER+RankMixer 约 0.6478，Full Transformer+RankMixer 约 0.6481；统一架构 MTGR/OneTrans（w/ Full Transformer）约 0.6483，仍低于 HyFormer。
  • 消融：query 里去掉“序列 pooling tokens”或去掉非序列上下文会造成 AUC 下滑；把多序列合并/共享 query 会损失（论文示例约 -0.06%）。
  • Scaling：随着 Params 或 FLOPs 增长，HyFormer 的提升斜率更陡，体现“更高 scaling efficiency”。

论文 vs 本仓库实现：多序列分支在 sample 数据上怎么落地

  • 论文语义分组：long-term/search/feed 是业务语义明确的三条序列。
  • 本仓库自动分组：TAAC sample 只有一组扁平的 domain_* 序列通道，于是用 round-robin 的方式均分成 --num-sequences 组，并对齐成 [B, S, L, F]。
  • 影响：这能让你在公开 sample 上跑通 HyFormer 的“接口与数据流”，但不等同于论文里真正的多序列语义建模难度。

对比：两种“统一”的差异到底在哪？

维度 OneTrans HyFormer
统一方式 把所有 token 拼成一个序列，直接堆 causal Transformer 变体。 保留多序列分支，但每层用 query 解码 + mixer 混合把交互拉进 backbone。
“序列信息”如何进入非序列？ 通过注意力与金字塔压缩，把信息逐层吸进前缀 ns_tokens。 通过 query decoding 把序列读到 queries，再通过 boosting/mixer 在 token 级混合。
参数化特点 混合参数化：前缀 token 特化 + 其余共享（attention 与 FFN 都如此）。 分支化：每个序列 encoder/decoder 独立；mixer 负责跨分支、跨 query 的混合。
长序列效率思路 通过 pyramid 逐层缩短 query 长度（降低后续层计算）。 通过“短序列表示 + cross-attn 解码 + 轻量 mixer”在每层做迭代优化。

Training & System Optimizations 深入解析

两篇论文在训练层面都做了大量系统级优化，以支撑工业级 CTR 预测的规模与时延要求。

OneTrans 训练优化

跨请求 KV 缓存

同一次请求的所有候选 item 共享相同的序列 token（S‑side），在第一次前向计算后将其 Key/Value 对缓存，后续每个候选只需计算 NS‑side 的查询并进行跨注意力。

金字塔查询压缩

每层只保留前缀 Q token（长度随层递减），显著降低 O(L·Q·d) 的注意力计算量。

FlashAttention‑2 & 混合精度

使用 FlashAttention‑2 实现内核级 I/O 合并，配合 BF16/FP16 与激活重算，显著降低显存占用并提升吞吐。

HyFormer 训练优化

稀疏特征压缩 (GPU Pooling)

对长序列特征做稀疏去重，仅在 GPU 上重建完整序列，减少 Host‑to‑GPU 拷贝和显存占用。

异步 AllReduce

梯度聚合与前向/反向计算交叉进行，导致 W_k = W_{k-1} + g_{k-1} 的一步延迟，但实验表明对收敛影响可忽略。

Query Boosting Mixer

每层将 decoded queries 与 non‑seq tokens 拼接后做 MLP‑Mixer，实现跨序列、跨特征的高效信息混合。
