先把推荐算法讲清楚

CTR 模型不是“猜用户喜欢什么”的玄学，而是在做一个很具体的二分类问题：给定用户、商品、场景和历史行为，预测这次曝光会不会被点击。

输入是什么

推荐模型会同时看静态信息和动态行为。静态信息像年龄段、城市、商品类目、价格；动态行为像最近看过、点过、买过、停留过什么。

用户画像 商品特征 上下文 行为序列

输出是什么

模型输出一个分数，比如 0.82。它通常可以理解成“当前用户点击当前候选内容的概率”。推荐系统会拿很多候选内容的分数排序。

CTR 排序分数 二分类

训练靠什么

每条曝光记录都有标签：点了是正样本，没点是负样本。模型不断比较“预测概率”和“真实点击”，把参数调到更会排序。

两个仓库的共同骨架

OneTrans_Pytorch 和 Hyformer_Pytorch 不是两个完全无关的工程。它们共享同样的三层结构：底层 backbone 写算法，中间 task wrapper 接 TAAC 数据，最外层 training script 负责跑训练。

Backbone

main_pytorch.py 放模型核心积木。OneTrans 这里是 token 压缩 Transformer；HyFormer 这里是序列编码、query decoding、query boosting。

Task Wrapper

models/taac_*.py 把 TAAC 特征变成模型需要的 token，再接一个分类 head 输出点击类别 logits。

Training Script

scripts/run_taac2026_sample.py 负责加载样本数据、切训练集验证集、AMP、训练循环、AUC 和 checkpoint。

OneTrans_Pytorch 默认把数据整理成 non_seq=(N, 183) 和 seq=(N, 16, 45)。非序列特征会变成 ns_len 个伪 token，行为序列每一步变成一个 seq token。
Hyformer_Pytorch 默认把序列特征分成 num_sequences=3 个分支，形成 seq=(N, 3, 16, 15)。每个分支都有自己的 query token 去读取该分支行为。
utils/taac_data.py 负责 schema 检测、数值清洗、序列 padding、数组统计特征。HyFormer 版本额外做了 sequence grouping。

它到底做了什么

仓库里的 TAACOneTransClassifier 先用线性层把 non_seq 变成 ns_len 个伪 token，把 seq 的每个时间步变成序列 token，然后拼成 [ns_tokens, seq_tokens]。

MultiOneTransBlock 会做多组 OneTransBlock 并取平均。每个 block 里有 attention 和 FFN。特别之处是：前 ns_len 个 token 各自有一套参数，后面的序列 token 共用一套参数。

金字塔压缩阶段每次少看一个 query token，直到只剩 ns_len 个 summary token。最后 mean pooling，再接分类头。

统一建模 token 交互 逐步压缩 CTR head
1
电商例子 用户是“上海、常买数码、晚上浏览”，最近依次看了手机壳、充电宝、耳机。OneTrans 会把画像卡片和这三次行为卡片放在同一排，让“耳机”这张卡影响最终的用户兴趣 summary。
2
为什么要压缩 真实推荐里行为很长，全部保留会慢。OneTrans 像写会议纪要：每轮讨论后丢掉一点细节，但把有用信息吸收到 summary token 里。
3
mask 的直觉 mask 控制哪些 token 可以互相看。比如行为序列可以按时间只看过去，非序列 summary token 可以更自由地吸收全局信息。

HyFormer：先分行为频道，再派 query 去提问

HyFormer 的思路更像客服系统：不同类型行为放到不同频道，每个频道有一个专门的问题 query 去问“这个频道里哪些行为对当前推荐最重要？”问完以后再把所有答案和非序列特征混在一起。

它到底做了什么

TAACHyFormerClassifier 把非序列特征变成 num_non_seq_tokens 个 token，把序列特征按 num_sequences 分组，每组用自己的 tokenizer。

它先把所有序列做 mean pooling，加上原始非序列向量，形成 global_info。然后每个序列分支用一个 MLP 生成自己的 query token。

每层 HyFormer 先做 Query Decoding：query 通过 cross-attention 读取对应序列；再做 Query Boosting：把 query 答案和非序列 token 用 MLP-Mixer 风格模块混合。

query decoding query boosting 多序列 可换 encoder

longer

先把长序列按窗口压短，再用短 query 做 cross-attention。直觉是“先粗略分段，再挑重点”，更省计算。

full_transformer

标准 self-attention。序列内部每一步都可以互相看，表达力强，但长序列时计算更重。

swiglu

不用 attention，用门控前馈网络做序列表示。速度更轻，适合快速验证或计算预算紧张的场景。

两个算法怎么放在一起理解

它们都在解决 CTR 里的同一个核心问题：既要理解用户长期画像和候选商品，也要理解最近行为序列。区别是信息组织方式不同。

问题 OneTrans HyFormer
核心比喻 所有卡片坐一排开会，最后写成几张 summary 卡片。 每个行为频道派一个 query 去提问，再把答案汇总。
输入组织 [ns_tokens, seq_tokens] 拼成一条 token 序列。 非序列 token 单独保留，行为序列分成多个 branch。
序列处理 序列 token 在统一 Transformer 里参与交互，然后被逐步压缩。 每个序列 branch 先编码，再由 query cross-attention 读取。
特征交互 attention + FFN，非序列 token 有独立参数组。 query decoding 后，用 QueryBoostMixer 混合 query 和非序列 token。
适合理解成 “统一建模 + 信息压缩”的 Transformer CTR 模型。 “序列建模”和“特征交互”分工更清楚的 CTR 模型。
推荐算法小白的第一条主线

先别纠结论文名。你只要记住：推荐模型把用户、商品、上下文、行为序列变成向量；模型学习这些向量之间的关系；最后输出点击概率并排序。

看实验结果时的提醒

这个仓库用的是 TAAC2026/data_sample_1000 小样本，AUC 接近随机是正常现象。它更适合验证代码链路和理解算法框架，不适合证明模型最终效果。

三个实际例子

用生活里的推荐场景把“非序列特征”和“序列特征”分开看，会更容易理解两个模型为什么这样设计。

电商推荐

非序列特征：用户城市、会员等级、商品价格、品牌、当前时间。序列特征：最近浏览、收藏、加购、购买的商品序列。

模型怎么用

OneTrans 会把这些信息放到一条 token 流里压缩。HyFormer 会把浏览、加购、购买等行为分成不同频道，让 query 分别提取“最近真正想买什么”。

短视频推荐

非序列特征：用户设备、网络、地区、视频作者、视频主题。序列特征：最近看完的视频、快速划走的视频、点赞评论的视频。

模型怎么用

如果用户刚连续看了健身内容，序列 token 会强烈影响当前分数。但如果候选视频和用户长期兴趣冲突，非序列 token 也会参与修正。

本地生活推荐

非序列特征：城市、距离、价格、营业状态、是否周末。序列特征：最近搜索的商圈、点击的店铺、购买过的券。

模型怎么用

午饭时间看到轻食券和深夜看到火锅券，点击概率不一样。上下文特征和行为序列一起决定排序。
